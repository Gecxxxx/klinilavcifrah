# Этап 3 — устойчивое сохранение заявок на VPS

Реализация подготовлена в отдельной ветке. До серверной установки и слияния PR
основной сайт продолжает использовать прежний Cloudflare Worker. Изменение исходников
само по себе не означает, что реестр уже подключён к production.

## Путь заявки

`POST /api/leads` → Nginx → приватный Gunicorn на `127.0.0.1:3090` → SQLite.
Заявка и задание очереди сохраняются одной транзакцией с `synchronous=FULL`.
Только после успешного COMMIT возвращаются `ok=true`, `saved=true` и ID реестра.
Ответ не зависит от доступности Telegram. Публичного чтения/выгрузки реестра нет.

Сервер проверяет формат/размер JSON, поля, контакт, согласие, honeypot и Origin;
ограничивает новые записи по хешированному IP и общему числу за минуту.
Новый интерфейс сохраняет requestId для повторов, в том числе после потери ответа
и перезагрузки страницы при доступном sessionStorage. Параллельные повторы одного ID
возвращают ту же запись; изменение содержимого с тем же ID даёт 409.
Для уже открытых старых форм без ID действует эвристическая дедупликация одинакового
нормализованного содержимого за 10 минут. Это не полноценная идемпотентность старого клиента.
При запрещённом sessionStorage повтор в той же вкладке поддерживается в памяти;
после перезагрузки такой вкладки идентификатор восстановить нельзя.

Хранятся поля обращения, page/referrer/UTM/landingPage, время сервера и согласия,
идентификатор текущей редакции политики, статус, ответственный и следующее действие.
Идентификатор политики явно помечен как pending-review: утверждённых юридических
документов и реквизитов этот этап не создаёт. Форма просит не указывать данные пациентов.
Контакты и содержимое формы не передаются в параметры аналитических событий.
`lead_saved` отправляется после подтверждения записи; повторное подтверждение одного ID
в текущей сессии не дублирует это событие.

## Уведомления

Отдельный systemd timer каждую минуту забирает очередь с ограниченной арендой задания.
Получатели — только фиксированные chat_id из закрытого серверного файла;
публичный `/start` не добавляет получателей нового реестра.
Журнал хранит попытки и код отказа без токена и текста ответа провайдера.
Успех каждого получателя фиксируется отдельно: при частичном отказе повторяется только
недоставленное. Есть backoff, учёт Retry-After, восстановление после истечения аренды,
12 попыток до attention и ручной повтор. При attention сервис выдаёт ошибку для мониторинга.

В уведомлении указан ID реестра. При потере ответа Telegram или остановке процесса
между фактической отправкой и фиксацией результата возможен повтор уведомления с тем же ID.
Telegram не предоставляет здесь гарантии exactly-once; запись заявки при этом не удваивается.

## Файлы и доступ

| Назначение | Путь |
| --- | --- |
| База и WAL | `/var/lib/kvc-leads/leads.sqlite3` и соседние SQLite файлы |
| Закрытый конфиг | `/etc/kvc-leads.env`, root, 0600 |
| Служебный пользователь | `kvc-leads`, без shell/SSH/sudo |
| Приватный код | `/opt/kvc-leads/app/current` → отдельный релиз |
| Зависимость | Gunicorn 26.2.0, официальный wheel с закреплённым SHA-256 |
| Локальные копии | `/var/backups/kvc-leads`, закрытый каталог |
| Команды оператора | `kvc-leads` из личного root-сеанса |

Статический деплой, откат кода и очистка старых релизов не включают каталог базы.
Новый API публикуется отдельным проверяемым архивом. Файлы backend не попадают в `out/`.
Пользователь `kvc-deploy` не получает sudo и не читает закрытый конфиг/базу.
Он переключает API-код и записывает фиксированный сигнал перезапуска; root-owned
systemd unit перезапускает только сервис API, работающий от `kvc-leads`.
Доступ к публикации кода подразумевает доверие к этому коду как к обработчику заявок.

## Порядок первого подключения

1. Подготовить токен существующего бота и доверенные числовые chat_id получателей.
   Не отправлять токен в чат, GitHub или командную строку. Установщик запрашивает его
   скрыто в интерактивном SSH; ввод chat_id выполняется рядом. Проверяет только
   read-only getMe/getChat. Ни заявка, ни тестовое сообщение при установке не отправляются.
2. Запустить скрипт из проверенного полного SHA ветки этапа 3. В PowerShell на ПК:

```powershell
ssh -t -4 -o ConnectTimeout=15 -i "$env:USERPROFILE\.ssh\id_ed25519_kvc" root@89.124.104.188 "curl -fLo /tmp/kvc-setup-leads.py https://raw.githubusercontent.com/Gecxxxx/klinilavcifrah/COMMIT_SHA/deploy/setup-leads.py && python3 /tmp/kvc-setup-leads.py COMMIT_SHA"
```

3. Скрипт сохраняет конфиг Nginx, создаёт отдельный сервис/реестр, проверяет API,
   делает SQLite backup и проверяет его восстановление в отдельной базе.
   Затем меняет только location `/api/leads`, выполняет `nginx -t`, reload и проверяет
   публичные OPTIONS и revision. На ошибке переключения возвращает прежний обработчик;
   сохранённые записи не удаляет. Ожидаемый итог: `DURABLE API READY` и статистика.
4. После подтверждения установки слить PR в main. Новый workflow сначала публикует API
   и подтверждает его локальную/public revision, затем публикует форму.
   Без `/opt/kvc-leads/enabled`, созданного root-установкой, публикация остановится.
   Это защита от выпуска новой формы перед подключением хранилища.
5. Повторить внешние GET/OPTIONS, сверить revision API и сайта. Проверку реальной
   тестовой заявки с уведомлением проводить отдельно после разрешения владельца;
   текущие интеграционные тесты используют изолированную БД и подмену/отключение Telegram.

Секрет Turnstile по умолчанию не задан: сохраняются honeypot и rate limits.
Если Turnstile включается, серверный `TURNSTILE_SECRET_KEY` и публичный ключ виджета
должны быть настроены согласованно. Для валидного повторного requestId уже сохранённой
заявки одноразовая CAPTCHA повторно не требуется.

## Работа с реестром

В личном root SSH-сеансе:

```bash
kvc-leads stats
kvc-leads list
kvc-leads retry LEAD_UUID
kvc-leads update LEAD_UUID --status contacted --responsible 'Ответственный' --next-action 'Связаться' --next-date '2026-10-22T10:00:00+03:00'
kvc-leads export /var/lib/kvc-leads/export-private.jsonl
systemctl status kvc-leads-api kvc-leads-notify.timer kvc-leads-backup.timer --no-pager
```

`list` показывает ID/статусы/следующее действие без контакта; закрытый JSONL содержит полную
запись. Выгрузка создаётся с 0600 и не перезаписывает существующий файл.
Токен и поля заявки не выводятся в журналы API. Телефон/адрес источника не передаются в URL API.

## Резервирование и откат

Ежедневный SQLite backup выполняется штатным backup API, а не копированием открытого
файла без WAL. Копия проверяется integrity_check и изолированным восстановлением.
Хранятся до 7 локальных копий в пределах 64 MiB, либо одна последняя копия большего размера.
При нехватке места backup останавливается с ошибкой; актуальная база не заменяется.
Размер реестра ограничен 128 MiB, новые записи отклоняются без успеха при нехватке места.
Старые лиды автоматически не удаляются: сроки хранения должен определить оператор.

Копии на том же VPS защищают от ошибки изменения, но не от потери всего сервера.
Отдельное закрытое внешнее резервирование и окончательная политика хранения ещё нужны.

При сбое новой версии deploy-api возвращает ссылку к прежнему API-коду и подаёт сигнал
его перезапуска. SQLite остаётся на месте. Нормальный откат интерфейса также не возвращает
Nginx на обработчик без реестра. Не восстанавливать старую БД поверх новых обращений.
Перед восстановлением после аварии: остановить запись, сохранить текущую БД с WAL,
проверить копию отдельно и согласовать объединение записей; автоматического merge лидов нет.

Старый Cloudflare Worker и Node API в репозитории — прежние варианты, не реализация этого
реестра. Их нельзя считать устойчивыми или повторно подключать к формам без миграции.
После переключения основного сайта следует отдельно отключить приём лидов на старом Worker
и устаревших Pages-превью либо подключить их к подтверждённому хранилищу.
Текущих прав на публикацию Worker у агента нет; изменение Nginx не выключает его внешний URL.

## Доказательства локальной проверки

- 16 тестов API/SQLite: все 5 страниц, реальные транзакции, 16 конкурентных повторов,
  потеря ответа и перезапуск, конфликт ID, валидация, CAPTCHA, постоянный rate limit,
  падение записи в outbox с rollback заявки, отказ/частичная доставка/Retry-After,
  attention/manual retry, истечение аренды и отдельное восстановление backup.
- 18 тестов операций: включая упаковку приватного API, повреждение/симлинк,
  откат кода при ошибке/прерывании, сохранность внешней базы и точечную правку Nginx.
- 3 теста клиентского requestId: повтор, редактирование, подтверждение,
  недоступный/повреждённый sessionStorage и отсутствие сырого контакта в сохранённом состоянии.
- Изолированный Gunicorn 26.2.0 + SQLite + статический сайт + Playwright:
  55 passed, 1 skipped. Включает сохранение через все 5 форм в desktop/mobile,
  потерю уже полученного сервером ответа, 503/старое неподтверждённое подтверждение,
  двойное нажатие и прежние smoke-проверки. Первый параллельный прогон имел два сбоя
  локального Chromium; последовательный полный прогон прошёл. Внешний Telegram не вызывался.
- Static build, lint/typecheck, SEO экспорта, Actionlint и systemd-analyze verify.

Это проверка подготовленного кода и стенда. Установка systemd, фактическая память/диск,
сигнал перезапуска API и подключение Nginx на действующем VPS требуют серверного запуска.
Этап не объявляется завершённым на production до этого подтверждения.
