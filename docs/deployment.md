# Публикация и откат сайта

Основной адрес: `https://klinikavcifrah.ru`. Состояние публичной инфраструктуры и ограничения проверки описаны в [отчёте этапа 1](stage-1-status.md).

Для GitHub Actions → действующий VPS подготовлена [инструкция одноразового подключения](github-vps.md).
До установки отдельного ключа и включения `KVC_DEPLOY_ENABLED` автоматическая публикация не активна.

## Режимы сборки

| Размещение | Команда | Результат | Обработчик формы |
| --- | --- | --- | --- |
| Статика на Nginx | `pnpm build:static` | `out/` | По умолчанию `/api/leads` на основном домене; сохранить существующий серверный маршрут |
| Cloudflare Pages | `pnpm build:pages` | `out/` | Явно заданный в команде отдельный API Worker |
| Next.js на Node.js | `pnpm build` и `pnpm start` | `.next/` и зависимости приложения | Next.js `/api/leads` |
| OpenNext Worker | `pnpm build:cf` | `.open-next/` | API внутри Worker |

Эти режимы не взаимозаменяемы при публикации. Не заменять действующую конфигурацию сервера или обработчик формы без проверки. Pages/статический экспорт не содержит серверных API-файлов.

## Подготовка релиза

1. Зафиксировать commit SHA. Использовать Node.js 22+ и `pnpm install --frozen-lockfile`. Не обновлять зависимости одновременно с выпуском правок.
2. Для основного сайта установить `NEXT_PUBLIC_SITE_URL=https://klinikavcifrah.ru`. Это также безопасное значение по умолчанию. Сборка с HTTP или localhost в production завершается ошибкой. Для отдельного стенда допускается явный HTTPS origin.
3. Для статики на текущем Nginx оставить `NEXT_PUBLIC_LEADS_API_URL` пустым, если подтверждён существующий `/api/leads`. Не менять его на workers.dev без необходимости.
4. Выполнить `pnpm lint`, `pnpm test:site-url`, затем нужную сборку. Для экспорта выполнить `pnpm check:seo`; для Node.js после сборки — `pnpm typecheck` и применимые Playwright-проверки.
5. Собрать экспорт ровно один раз и передавать тот же проверенный артефакт на стенд и сервер. `NEXT_PUBLIC_*` встраиваются при сборке: изменение переменной на сервере без пересборки не исправит старый HTML/JS.
6. На изолированном стенде проверить все девять URL, 404, CSS/JS, изображения и OG image. Не отправлять настоящие заявки при проверке этапа 1.

Для артефакта статического релиза из корня проекта:

```bash
mkdir -p release-artifacts
git rev-parse HEAD > release-artifacts/source-commit.txt
tar -czf release-artifacts/site.tar.gz -C out .
sha256sum release-artifacts/site.tar.gz > release-artifacts/site.tar.gz.sha256
```

Каталог `release-artifacts/` исключён из Git. Не помещать в архив `.env`, `.dev.vars`, токены, заявки или конфигурацию сервера.

## Действия на сервере

Перед изменениями администратор должен определить действующие `server_name`, TLS certificate, document root и маршрут `/api/leads` по `nginx -T`. Конфигурация может содержать чувствительные сведения: не публиковать полный вывод в GitHub.

Сохранить отдельно действующий статический релиз, конфигурацию Nginx и конфигурацию обработчика. Секреты хранить в защищённом резервном хранилище. Если есть хранилище заявок — получить его согласованную резервную копию и проверить восстановление в отдельную тестовую базу. Git-ветка сохраняет только исходный код и не заменяет эти копии.

Развернуть новый артефакт в отдельный каталог релиза. Проверить его на стенде до переключения document root или ссылки на текущий релиз. Не копировать новый `out/` поверх работающего каталога: старый релиз нужен для быстрого возврата. Существующие API proxy, TLS и журналирование сохранить.

Для www использовать [canonical-host.inc](../deploy/nginx/canonical-host.inc) внутри действующего HTTPS `server`, обслуживающего оба имени. В сертификате должны присутствовать оба имени. Фрагмент добавляет только постоянный редирект www → apex и сохраняет `$request_uri`, включая путь и UTM. Рабочий HTTP → HTTPS редирект менять не требуется, если проверка подтверждает его корректность.

После правок конфигурации:

```bash
sudo nginx -t
sudo systemctl reload nginx
```

Выполнять reload только после успешного `nginx -t`. После переключения повторить GET-проверки основного домена: HTML canonical/OG/JSON-LD, sitemap, robots, 404, загрузка ресурсов, редиректы HTTP/www с вложенным путём и query. OPTIONS `/api/leads` проверяет маршрут, но не доказывает доставку или сохранение заявки.

## Откат

1. Вернуть ссылку или document root на предыдущий каталог статического релиза.
2. При изменении Nginx восстановить его сохранённую конфигурацию, выполнить `nginx -t` и только затем reload.
3. Не откатывать и не перезаписывать хранилище новых заявок вместе с сайтом. Не менять обработчик/API и его секреты, если они не участвовали в релизе.
4. Проверить страницу контактов, ресурсы, 404 и маршрут API. Зафиксировать причину возврата и SHA релиза.

## Прерванный статический билд

Скрипт временно переносит `src/app/api` в `.pages-api-disabled` и восстанавливает в `finally`. Если процесс принудительно завершён и API не восстановлен либо две копии различаются, новая сборка остановится, не удаляя сохранённые API-файлы. Идентичный остаточный каталог очищается только после сравнения всех файлов. При отсутствии `src/app/api` восстановить его:

```bash
mv .pages-api-disabled src/app/api
```

Если существуют оба каталога, сначала сравнить их содержимое и восстановить корректную версию; не удалять ни один автоматически. Не выполнять параллельные сборки в одном checkout.
