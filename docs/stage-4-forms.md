# Этап 4 — формы, атрибуция и аналитика

## Поведение формы

- Клиент и VPS принимают телефон (от 6 цифр), email, @Telegram и t.me-контакт.
  Проверяются границы: имя 100, компания 160, контакт 100, сайт 300, задача 1000.
- Обязательные поля обозначены. Ошибки связаны с полями через aria-describedby;
  отправка с ошибкой переводит фокус к первому полю. У каждой формы свои ID.
- Во время запроса поля заблокированы. Повторное нажатие не создаёт второй запрос.
  На сетевой ошибке/429 значения остаются; повтор сохраняет исходный requestId.
- Успех показывается только после saved=true с ID, затем форма очищается.
  Фокус переходит к подтверждению/серверной ошибке. Сбой аналитики не меняет этот результат.
- Политика открывается в новой вкладке, чтобы заполненная форма оставалась на месте.
- Turnstile, если настроен, создаётся отдельно для каждой формы и удаляется при уходе.
  Просроченный токен сбрасывается; компактный вид помещается на 320 px.
  Этот этап не включает CAPTCHA на production: публичный ключ и серверный секрет должны
  задаваться согласованно. Обычные honeypot и серверные ограничения продолжают работать.

## Источник обращения

В рамках вкладки фиксируется первый вход: landingPage, внешний referrer без query/hash
и пять стандартных UTM (до 200 символов). Данные сохраняются в sessionStorage и переживают
внутренние переходы/перезагрузку. Последующие ссылки с UTM не переписывают первый источник.
Без внешнего источника значение пустое — оно не выдаётся за рекламный канал.

CTA сохраняет страницу и место перехода, продукт preliminary_review и направление:
marketing, digital, commercial или general. Это текущий предварительный разбор;
утверждённый каталог 11 услуг и цены этот этап не меняет и не придумывает.

Сведения уходят в приватный SQLite-реестр вместе с заявкой. В уведомлении видны
направление и страница перехода. При повторе неопределённого запроса сохраняется
исходная атрибуция, а не источник более позднего перехода. Новые метаданные не
изменяют исходную схему fingerprint: повтор совместим и с предыдущей версией API.
Метаданные добавляются только при наличии в запросе, чтобы не менять fingerprint
старых уже открытых форм и не нарушать их идемпотентные повторы.

При запрещённом хранилище остаётся память текущего документа: текущий UTM и переходы
SPA работают. После полной перезагрузки без storage первоначальный источник восстановить
невозможно. Контакты и текст задачи в sessionStorage не сохраняются; pending request
содержит хеш значений, ID и атрибуцию.

## Метрика

GitHub Actions читает публичную Repository variable `NEXT_PUBLIC_YANDEX_METRIKA_ID`.
Пустое значение допускается и явно отмечается в CI: заявки/источники работают, внешняя
Метрика выключена. Неверный формат ID останавливает сборку. Номер нельзя выдумывать:
для включения нужен реальный счётчик владельца. Сам код не создаёт счётчик и цели в кабинете.
После добавления variable нужно повторить сборку/деплой актуального main.

| Событие | Когда и что передаётся |
| --- | --- |
| Просмотр страницы, hit | При первом входе и SPA-переходе; известный путь без query/hash |
| cta_click | Размеченные кнопки в hero, шапке, меню, футере и на страницах направлений |
| form_start | Первый фокус в полях/кнопке текущего заполнения |
| form_submit | Валидная форма перед сетевой отправкой |
| form_error | Категория: validation, captcha, server_validation, rate_limit, conflict, server, unconfirmed, network, timeout; при локальной ошибке — имена полей |
| lead_saved | Только после подтверждения записи; один раз на ID в сессии |
| form_success | Совместимое прежнее событие того же подтверждения |

Основной конверсией следует выбрать lead_saved, а не одновременно lead_saved и form_success.
Параметры событий ограничены контекстом интерфейса; контакт, имя, компания, задача,
UTM, ID заявки и сырой URL в них не передаются. Webvisor выключен, поля дополнительно
помечены ym-disable-keys. Начальные события ставятся в очередь до загрузки счётчика;
отказ счётчика/блокировщик не влияет на форму. Для локальной проверки есть CustomEvent
kvc:goal с тем же ограниченным набором параметров; это не доказательство поступления
события в настоящий кабинет Метрики.

Коммерческие статусы (qualified, negotiation, contract, paid и др.) остаются в независимом
реестре; изменяются закрытой командой kvc-leads update. Внешний счётчик не является
источником правды об обращениях.

## Проверки

- 5 Node-проверок: совпадение клиентских/серверных форматов и границ, первый источник,
  переход CTA и reload, отключённое/повреждённое хранилище, очередь Метрики и отказ счётчика.
- 3 проверки клиентского requestId, 31 API/SQLite/бота, 24 проверки операций.
- Браузерный стенд: отдельные Gunicorn, SQLite и статический экспорт. Полный прогон:
  63 passed, 7 skipped (визуальные сценарии по флагу и мобильный сценарий в desktop-проекте).
  Telegram не вызывался, production-заявки и реальные события в Метрику не отправлялись.
- После окончательной правки блокировки полей — 26 passed в отдельном прогоне всех сценариев форм,
  включая сохранение, потерю ответа, отказ storage, источник после reload и недоступную аналитику.
  В первых финальных попытках локальный Chromium падал в Skia/fontconfig до загрузки
  страницы; для повторной проверки настроен отдельный fontconfig с установленными шрифтами.
- Lint, typecheck, static build, SEO 9 страниц. Состояние публикации подтверждается
  успешным workflow и совпадением __release.json / X-KVC-API-Revision на основном домене.
